# Audit 2026-09-03 — member lifecycle & Drive subsystem (v5 → v6 input)

**Method:** full read of proposal.md, ROADMAP.md, all `src/coordinator/` modules,
scripts, prompts/skills, compose, seed/config artifacts, phase-gate docs, git history;
Hermes-capability claims verified against upstream docs (hermes-agent.nousresearch.com
+ GitHub at our pin's lineage). No production code was touched.

**Verdict:** engineering discipline (TDD, timezone law, review protocol, test suite) is
excellent. Two architecture-level seams are broken: (A) member onboarding is
internally inconsistent — its own canonical runbook produces a half-member; (B) the
Drive subsystem rebuilds a capability Hermes ships as a skill. Plus a handful of
YAGNI violations. This document is the durable record the v6 restructure executes
against.

---

## A. Member lifecycle

### A1. `member_add` never asks for the Telegram ID — by design, in three places
- `src/coordinator/handlers.py:34` (`_ADD_FIELDS`) and `:205` — required = `{name,
  timezone, wake}`; `telegram_id` optional, `null` treated as absent.
- `src/coordinator/hermes_plugin.py:98` — model-facing schema: `"required":
  ["name","timezone","wake"]`; the tool description doesn't mention `telegram_id`.
- `prompts/persona.md` + skills — nothing instructs the agent to ask for it.

Consequence: "Add the member Luis…" creates a row with `telegram_id = null`, which is
the join key for self-service (persona rule 4) and check-in greeting routing. An
ID-less member is an inert row.

### A2. The canonical onboarding runbook collects the ID and then discards it
`proposal.md` §8.2: step 1 collects the member's Telegram user ID; step 2 spends it on
`TELEGRAM_ALLOWED_USERS` (env + gateway restart); step 3's example command — *"add
Rita — backend, America/Guayaquil, wake 09:00"* — **omits the ID step 1 collected**.
Following the procedure exactly produces: allowlisted at the gate, anonymous in the
DB, no self-service, no routable check-in. The conversational onboarding loop the
owner experiences (asking, patching via `member_update`, restarting) is this design
gap, not an agent failure.

### A3. "Add Luis" today creates a duplicate Luis
Luis exists in `config/members.seed.yaml:19` with `telegram_id: null`. No name
uniqueness anywhere (`schema.sql` UNIQUE is only on `telegram_id`; neither
`handlers.member_add` nor `MembersRepo.add` checks names). The T1.9-prescribed
"jobs are created conversationally at onboarding" path inserts a second Luis, a
second `checkin-5`, and a roster showing two of him. The correct path (complete the
seeded row via `member_update`) is documented nowhere.

### A4. Two sources of truth for "who is a member"; the real one needs a restart
Proposal's headline promise (lines 4–5, §1): *no restart for everyday changes*;
*adding a member = one Telegram message*. The actual access gate is
`TELEGRAM_ALLOWED_USERS` — compose env, one line + gateway restart per new member
(`.env.example` says so verbatim; upstream ties the env to gateway restart). The DB
`members` table is a directory *behind* the gate, not the gate. Keeping the gate
env-owned is defensible (the agent must never edit its own authorization) — but then
the DB side had to be airtight, and it is the sloppiest part instead (A1–A3).

### A5. Seed file defects
- 3 of 4 `telegram_id`s are `null` → ¾ of the roster inert (only `checkin-1` exists,
  per the T1.9 Pi note).
- A real personal Telegram ID (Juan, [redacted-founder-id]) is committed to the public template
  repo — and lives in git history. **Owner decision required** (out of scope for the
  restructure): accept, or purge history (BFG/filter-repo) — note the repo was also
  renamed (hermes-setup → finki-coordinator), old URL redirects.
- Dual identity: sold as "bootstrap seed example" (proposal §2 table) while acting as
  the real roster. Real roster belongs in a gitignored local file; the committed file
  should carry placeholders.

### A6. Missing tool paths the repo's own verification needs
- No delete: the phase-1 gate cleanup (`docs/verify/phase1.md:197-200`) instructs a
  human to run raw `sqlite3 DELETE FROM members WHERE id>4` — the gate procedure
  bypasses the tool surface.
- `generate_agents_md.py` is wired to nothing: roster changes don't regenerate
  `data/project/AGENTS.md` (cheap fix: a digest-job step).

### A7. Routing consequence
The cron relay carries no delivery target, and a `null` telegram_id leaves the system
no way to route a check-in greeting. Phase-1 evidence (phase1.md:125): fake members'
greetings arrived **in the owner's DM**. Members onboarded the §8.2 way would have
their check-ins delivered to whoever created the job. Note: the agent can see the
sender's Telegram ID in-session (self-service matching already depends on it), so
both the @userinfobot relay and the null-ID state are avoidable.

## B. Drive subsystem — reinventing a shipped skill

Verified upstream: the **google-workspace skill** exists with exactly the interface
the Hermes conversation described (`$GAPI drive search/get/download/upload`,
agent-driven setup, auto token refresh, native files export to text-friendly formats);
Hermes' own session store uses **SQLite FTS5**; **native cron** is already used by
this project. Proposal §4's "Hermes built-ins relied on (verified)" missed the single
most relevant built-in for this subsystem.

| Template builds | Hermes-native equivalent |
|---|---|
| manual OAuth client + refresh token | agent-driven skill setup, auto refresh |
| 5–6 env vars (`GOOGLE_DRIVE_*`, `RCLONE_*`) | one skill-managed credential |
| rclone on the Pi **host** (phase2 precondition) | nothing |
| `setup.sh` step 3 writes rclone.conf — 2 bug-fix commits deep (601b526, f905c4f) | — |
| 173-line `sync.sh` + resync guardrails | (escalation only, if ever) |
| host `crontab -e` cadence | Hermes cron, in-container |
| planned T4.2 bisync-recovery runbook + conflict drill + backup scope | not needed |
| proposal risk #9 = bisync eats files | risk eliminated by not using bisync |

Additional defects in the current design:
- **Container/host split-brain:** `sync.sh` runs host-side, but
  `prompts/skills/digest/SKILL.md` step 6 tells the *in-container* cron agent to run
  `scripts/sync.sh` — a path that does not exist inside the container (compose mounts
  only `src/coordinator`, `data/`, `~/.hermes`). Dead instruction.
- **Footgun default:** `RCLONE_ROOT_FOLDER_ID` empty (current Pi state) means the
  baseline would bisync the **entire Drive root** ⇄ `data/project/`.
- **Nothing ever ran:** T2.4 unchecked; rclone not installed on the Pi. The sunk cost
  is one wrapper script + its tests. Deleting now is the cheapest it will ever be.

**Honest counterpoint:** bisync's one unique value is automatic bidirectional
propagation (browser edits flow down, agent files flow up). With `$GAPI` the up-path
is `drive upload` and the read-path is live `download` — for 4 people and dozens of
text docs, the rclone/conflict/recovery tax buys little.

## C. Smaller KISS/YAGNI findings

1. **`status_days` is a dead column** — schema.sql:12, repos, `Member` dataclass, yet
   explicitly *rejected* as a payload field (tests/unit/test_handlers.py:572 asserts
   the rejection). No tool can ever set it. Violates the repo's own rule 8.
2. **`digest_time` can drift silently** — `setting_set` writes the DB, emits no cron
   relay (T0.8 "future need"); the actual digest job schedule is edited separately.
   Same drift class the proposal refuses to tolerate elsewhere.
3. **Compose passes all 6 Drive env vars into the container** although rclone runs
   host-side — dead env surface, dutifully pinned by test_compose.py's PASSTHROUGH
   list.
4. **README stale:** Phase 1 shown "🚧 manual gate" — phase1.md is signed off, T1.6 `[x]`.

## What is genuinely good (calibration)

`scheduling.py` survived a real adversarial red team (Lord Howe half-hour DST,
Kathmandu +05:45, year-2500); the cron_relay law (LLM never does timezone math) is
the right architecture; pure-core/impure-shell consistently enforced; 224+
deterministic tests; WAL + busy_timeout; the two-axis fresh-context review protocol;
evidence discipline in the Notes log. The engineering is not the problem; the two
seams are.

## Directives proposed for v6 (owner to confirm in the kickoff prompt)

- **D1 — Member onboarding redesigned around the DM the member already sends.** The
  member DMs the bot ("I'm Rita, backend, Quito, wake 09:00"); the agent uses the
  sender's Telegram ID from session context and creates a complete row via
  `member_add`. `member_add` demands a routable member (telegram_id required in
  schema/description/handler; reject duplicate active-member names). The owner's
  only manual step remains the env edit + gateway restart — the security boundary.
- **D2 — rclone bisync removed; Hermes-native google-workspace skill instead.**
  Tier 0 only: live `$GAPI` retrieval, no local mirror, no sync script, no FTS5
  index, no vector RAG. Escalation triggers documented, not implemented (YAGNI).
  Ordering note: deletion is safe because bisync never ran in production (T2.4
  unchecked) — but the new phase-2 gate MUST verify `$GAPI` works in-container at
  HERMES_REF before sign-off; if it does not, that is a stop-and-report condition,
  not an improvisation license.
- **D3 — Seed hygiene.** Placeholders in the committed seed; real IDs never
  committed; the leaked founder ID is flagged to the owner (history purge = owner
  decision, out of scope).
- **D4 — Dead weight cut.** `status_days` column (versioned migration);
  `digest_time` setting (default: drop — schedule edited conversationally; record
  alternative in Notes); compose Drive env passthrough; `sync.sh` + its tests;
  setup.sh's rclone.conf step; T4.2 bisync-recovery runbook task.

## Design decisions to settle in the restructure's DOC task

1. **Knowledge layout split:** Drive holds team-edited docs
   (brief/decisions/meetings/howto — edited in the browser, read live via `$GAPI`);
   local `data/project/` holds agent-owned files (generated `AGENTS.md`, `journal/`,
   inbox drafts). The runtime AGENTS.md query map is rewritten accordingly.
   *Recommended default as stated.*
2. **Journal flow stays local-first:** the digest's group post is the consumption;
   Drive upload of journals is a documented future trigger, not built.
3. **`member_delete`:** include (owner-only) — justified by actual gate usage
   (phase-1 cleanup used raw SQL; it is also the duplicate-row remedy).
4. **`digest_time`:** drop vs relay — default drop (see D4).
